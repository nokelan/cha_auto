# 07. 시퀀스 다이어그램

- 기준일: 2026-10-26
- 기준: 리팩토링 후 실행 코드; 다이어그램은 주요 호출·실패 분기를 추린 논리 흐름
- 관련: [DB 설계서](03_DB_설계서.md), [API 명세서](04_API_명세서.md), [클래스 다이어그램](06_클래스_다이어그램.md)

## 1. 실행 주체와 공통 작업 계약

로컬 HTTP API와 사이트 자동화는 별개다. API는 FastAPI에서 요청을 받고, 주요 작업은 `JobRunner`의 단일 작업 스레드에서 실행한다. 앱 창용 `app-profile`과 그룹웨어 사이트용 `browser-profile`도 별개다. 다이어그램의 Site는 전용 Playwright 브라우저와 그룹웨어를 묶어 표현한다. API의 200 작업 ID 응답은 작업 완료를 뜻하지 않는다. 근거: `launcher.py:106`, `saebom/jobs.py:35`, `saebom/services/core.py:24`.

`Service.submit`은 작업 실행기 위임이며, 실행기는 작업 상태를 `meta.jobs`에 저장한다. 화면은 `/api/state`를 다시 읽어 완료를 확인하고 비교 결과·가져온 계약·로컬 대조 결과를 해당 API로 조회한다. 아래 비동기 다이어그램의 200 반환과 작업 시작은 실제로 경쟁할 수 있다. 근거: `saebom/jobs.py:78`, `saebom/services/core.py:89`.

## 2. 시작·중복 실행·잠금 해제

```mermaid
sequenceDiagram
    actor User as 사용자
    participant L as launcher
    participant DB as Store
    participant API as FastAPI
    participant UI as 앱 Chromium
    User->>L: 실행
    L->>DB: Store 생성 및 스키마 검사
    L->>L: Mutex 확보
    alt 이미 실행 중
        L->>API: 기존 instance로 활성화 요청
        API->>UI: activate 이벤트
        L-->>User: 기존 창으로 복귀
    else 첫 실행
        L->>API: 임의 로컬 포트와 실행 토큰으로 시작
        L->>UI: 토큰 URL로 앱 창 열기
        UI->>API: GET /?token=실행토큰
        API-->>UI: 303 및 실행 쿠키
        UI->>API: GET /api/auth/status
        API-->>UI: authenticated=false
        User->>UI: 비밀번호 입력
        UI->>API: POST /api/auth/login
        alt 정답이고 잠금 시간 아님
            API-->>UI: 200 및 잠금 해제 쿠키
            UI->>API: GET /api/state
            API-->>UI: 목록과 작업 상태
        else 비밀번호 불일치
            API-->>UI: 401, 연속 실패 횟수 갱신
        else 잠금 시간 중
            API-->>UI: 429, 남은 초 안내
        end
    end
```

로그인 연속 실패가 5회면 이후 30초 잠금이며 잠금을 거는 5번째 요청은 401이다. 실행 토큰과 잠금 해제 토큰은 서버 재시작마다 새로 만든다. 재시작 후 API가 401을 반환하면 화면은 로그인 상태를 다시 확인한다. 실행 쿠키까지 만료된 경우에는 실행 경로에서 창을 다시 열어야 한다. 근거: `saebom/api.py:85`, `saebom/api.py:116`, `saebom/api.py:177`, `launcher.py:37`, `launcher.py:53`, `launcher.py:76`.

```mermaid
sequenceDiagram
```

```mermaid
        UI->>API: POST /api/results/id/correct

    end
    API->>J: 비교 작업 접수

    S->>DB: 계산서와 계약서 일괄 조회
    S->>S: 파일 존재와 종료 요청 확인
    loop 각 연결
        S->>S: effective_invoice 사본 생성 및 보정 반영

```

비교는 네트워크·AI를 사용하지 않는다. 파일이 없으면 작업 failed이며 다운로드를 안내한다. 보정값은 원본 문서 추출값을 덮어쓰지 않고 `method='수동 보정'`, `previous`를 가진 결과 사본을 만든다. HTTP 보정 접수가 실패하면 화면의 보정 창을 유지한다. 근거: `saebom/services/compare_service.py:167`, `saebom/routes/compare.py:92`, `saebom/overrides.py:25`.

판정 우선순위는 일반 항목에서 불일치 → 확인 필요 → 일치다. 문서 오류는 먼저 처리한다. 총액 계약의 `period`는 분할 지급 이행 여부를 문서만으로 확정하지 않으므로 **항상 확인 필요인 의도된 정책**이다. 금액이 맞더라도 이 정책은 유지된다. 근거: `saebom/compare.py:186`.

## 8. 지출결의서 상신·검토·불확실성

```mermaid
sequenceDiagram
    actor User as 사용자
    participant UI as ExpenseModal
    participant API as contracts 라우트
    participant S as Service
    participant J as JobRunner
    participant Site as SiteClient
    participant R as expense 규칙
    participant DB as Store
    UI->>API: GET /api/contracts/id/expense
    API->>S: expense_draft
    S->>DB: 계약 원문과 마지막 approval 조회
    S->>R: draft
    API-->>UI: 적격 여부, 초안, 경고, approval
    User->>UI: 원문 확인과 수정 후 상신
    UI->>API: POST /api/contracts/id/expense
    API->>S: submit_expense
    S->>R: validate
    S->>J: submit (계약 거래처 강제 적용)
    API-->>UI: 200 작업 ID
    J->>S: run_expense
    S->>DB: 기존 상태를 없음과 새 검토 초기값으로 교체
    S->>Site: 기안 화면 이동, 입력, 첨부 후보 선택
    Site->>Site: 상신 버튼 클릭
    alt 작성본을 정상 읽음
        Site-->>S: 문서 ID, 번호, URL, 제목, 금액, 본문
        S->>R: review 및 parse_document
        R-->>S: 8항목 검토
        alt 모든 항목 일치
            S->>DB: 품의완료 및 approval 저장
            S-->>J: 품의완료 메시지
        else 검토 불일치
            S->>DB: 없음 및 site_draft=true 저장
            S-->>J: 검토 불일치 메시지
        end
        J->>DB: 작업 done 저장
    else 클릭 뒤 결과 확인 오류
        Site--xS: SubmitUncertain
        S->>DB: 없음, site_draft=true, error 저장
        S--xJ: 예외 재전파
        J->>DB: 작업 failed 저장
    else 클릭 전 오류 또는 사이트 명시적 거절
        Site--xS: 일반 예외
        S->>DB: 없음 및 error 저장
        S--xJ: 예외 재전파
        J->>DB: 작업 failed 저장
    end
    UI->>API: GET /api/contracts
    API-->>UI: status 및 approval
    Note over User,UI: site_draft가 있으면 사이트 확인 뒤 재상신
```

`품의완료`는 앱의 작성본 검토 완료 표기다. 실제 결재자의 승인 완료를 조회하는 상태가 아니다. 검토 항목은 작성본 금액·본문 합계·본문 공급가액·본문 세액·검산·업체명·사용기간·제목이다. 근거: `saebom/expense.py:111`, `saebom/services/contracts_service.py:171`.

버튼 클릭 뒤 결과 화면 대기·읽기 오류를 `SubmitUncertain`으로 감싼다. 단, 사이트 명시적 폼 오류는 일반 ValueError다. **click 호출 자체는 이 래핑 try 밖**에 있으므로 그 호출 중 발생한 오류는 일반 예외 경로가 될 수 있다. `site_draft`가 없다고 사이트 기안이 없음을 보장하지는 않는다. 실제 사이트 상태와 다를 수 있으므로 자동 재상신하지 않는다. 근거: `saebom/site.py:195`.

입력 검증 실패나 접수 충돌이면 `run_expense`에 진입하지 않아 기존 상태를 유지한다. 실행이 시작되면 이전 성공 상태를 초기화한다. 상신 함수 안에서는 종료 요청 플래그로 중간 중단하지 않으며, DB 저장 장애가 겹치면 사이트 결과를 로컬에 기록하지 못할 수 있다. 근거: `saebom/services/contracts_service.py:152`, `saebom/services/contracts_service.py:171`.

## 10. 저장 위치 변경

```mermaid
sequenceDiagram
    participant UI as 설정 화면
    participant API as system 라우트
    participant J as JobRunner
    participant DB as Store
    participant M as document_mover
    participant FS as 파일시스템
    UI->>API: PUT /api/settings
    API->>J: exclusive 저장 위치 변경 진입
    alt 진행 작업 또는 다른 배타 구간 또는 종료 중
        J--xAPI: ValueError
        API-->>UI: 400
    else 진입 성공
        Note over J: busy 표시, 실행기 잠금은 해제
        API->>DB: set_document_root
        DB->>DB: Store.lock 획득
        DB->>M: 새 경로 및 쓰기 검사
        loop 등록된 PDF
            M->>FS: 새 위치 복사 및 SHA256 검사
        end
        alt 복사와 검사 성공
            DB->>DB: 경로와 document_root 트랜잭션 확정
            DB->>M: 이전 파일 정리
            M->>FS: 대상과 다른 이전 파일 삭제
            Note over M,FS: 삭제 OSError는 무시, 새 경로 유지
            API-->>UI: 200 새 document_root
        else 확정 전 오류
            DB->>FS: 이번 이동에서 만든 대상 파일 정리
            DB--xAPI: 예외
            API-->>UI: 400 또는 미처리 내부 오류
        end
        Note over DB: Store.lock 해제
        API->>J: finally로 busy 해제
    end
```

논리 순서는 검사 → 복사·검증 → DB 확정 → 이전 파일 정리다. 응답 시점과 finally 정리는 표현상 간략화했다. 이동 구간에 새 작업은 기다리지 않고 400이며, DB 조회는 Store.lock 때문에 기다릴 수 있다. DB 자체·브라우저 프로필·거래명세서 xlsx·사용자 계산서 폴더는 옮기지 않는다. 근거: `saebom/routes/system.py:38`, `saebom/jobs.py:135`, `saebom/store.py:318`, `saebom/store.py:330`, `saebom/document_mover.py:96`.

## 11. 종료

```mermaid
sequenceDiagram
    actor User as 사용자
    participant UI as 앱 창
    participant API as FastAPI 및 Uvicorn
    participant S as Service
    participant J as JobRunner

    alt 종료 버튼

        UI->>API: POST /api/shutdown
        API->>API: should_exit=true 요청
        API-->>UI: ok=true
    else 앱 창 닫기
        User->>UI: 창 닫기
        UI->>API: 창 감시가 should_exit=true 설정
    end
    API->>S: lifespan 종료, close
    S->>J: close(cleanup)
    J->>J: closing=true, 새 접수 차단
    Note over J: 기존 작업 종료 대기, 강제 중단 없음
    J->>Site: 같은 작업 스레드에서 close
    J->>J: pool.shutdown(wait=true)
    API->>DB: close
    API-->>L: 서버 run 반환
    L->>L: 창 종료 대기, instance.json과 소켓과 Mutex 정리
```

closing은 `JobRunner.close` 시 설정된다. shutdown HTTP 응답 자체가 이미 모든 자원 정리를 마쳤다는 뜻은 아니다. 비교·동기화·가져오기 작업은 플래그 확인 지점에서 중단할 수 있지만 상신 함수는 실행 중 중단하지 않는다. 작업이 끝나지 않으면 종료 대기도 길어질 수 있다. 근거: `saebom/api.py:100`, `saebom/jobs.py:155`, `saebom/services/core.py:254`, `launcher.py:152`.

## 12. 작업 상태 전이

```mermaid
stateDiagram-v2
    [*] --> running : 접수 및 최초 저장
    running --> done : 작업 함수 정상 반환
    running --> failed : 작업 함수 예외
    running --> failed : 재시작 시 복원
    done --> [*] : 최근 20개 범위 밖 정리
    failed --> [*] : 최근 20개 범위 밖 정리
    note right of running
        queued 상태는 없음
        다른 running 또는 busy이면 새 접수 거절
        강제 중단 및 제한시간 없음
    end note
    note right of done
        검토 불일치도 정상 반환이면 done
        계약 품의완료와 별개
    end note
```

최종 상태 DB 갱신 실패 시 메모리에서 동일한 done/failed를 남긴다. DB에는 running이 남을 수 있으며 다음 실행에서 failed로 복원한다. 최근 20건 밖 작업 제거는 새 접수 때 수행한다. 근거: `saebom/jobs.py:35`, `saebom/jobs.py:78`.


### 1.1 데이터 루트 결정 순서

`Store.__init__`은 다음 순서로 데이터 루트를 정한다(`saebom/store.py:50`).

| 순서 | 조건 | 루트 |
|---|---|---|
| 1 | 생성자 인자 `root`가 비어 있지 않음 | 그 경로(테스트가 `tmp_path`를 넘김) |
| 2 | 환경변수 `SAEBOM_DATA_DIR`이 비어 있지 않음 | 그 경로 |
| 3 | 환경변수 `LOCALAPPDATA`가 있음 | `%LOCALAPPDATA%\SaebomCompare` |
| 4 | `LOCALAPPDATA`도 없음 | `Path.home()\SaebomCompare` |

`root or env or ...` 구조이므로 `SAEBOM_DATA_DIR`이 빈 문자열이면 3번으로 넘어간다. 루트와 그 아래 `documents/` 폴더는 생성 시 항상 만든다(`saebom/store.py:51-52`). 원본 PDF 보관 폴더(`meta.document_root`)는 이 루트와 별개다(5절).

## 2. 테이블

여섯 테이블 모두 열이 `TEXT`이고 `DEFAULT`가 없으므로 아래 표의 "기본값"은 모두 없음(`NULL`)이다. 열 구성은 `Store()`를 임시 폴더에 만든 뒤 `PRAGMA table_info`로 읽은 결과와 `CREATE TABLE` 문(`saebom/store.py:59-64`)을 1:1 대조했다.

### 2.1 `items` — 사이트 메일·계약 목록(최신 스냅샷)

| 열 | SQLite 타입 | 제약 | 기본값 | 내용 |
|---|---|---|---|---|
| `kind` | TEXT | PK(`kind`,`id`) 1번째 | 없음 | `"mails"` 또는 `"contracts"` |
| `id` | TEXT | PK 2번째 | 없음 | 사이트 행의 `data-id`(예 `M-01`, `C-2026-001`) |
| `data` | TEXT | 없음 | 없음 | 행 JSON(4.1절) |

| 구분 | 내용 |
|---|---|
| 쓰는 메서드 | `Store.snapshot(mails, contracts)` 한 곳(`saebom/store.py:80-85`). 호출은 `Service.sync`(`saebom/services/compare_service.py:21`). |
| 읽는 메서드 | `Store.items(kind)`(`saebom/store.py:94`). 호출처는 `catalog`, `validate_pairs`, `Store.set_document_root`(`saebom/store.py:406-407`). |
| 교체 규칙 | 같은 트랜잭션에서 `DELETE FROM items` 후 `INSERT INTO items VALUES(?,?,?)`로 전부 다시 넣고 `meta.synced`를 갱신한다. `INSERT`에 `OR REPLACE`가 없어서 한 목록 안에 같은 `id`가 둘이면 `IntegrityError`가 나고 트랜잭션 전체가 취소되어 이전 스냅샷이 남는다(임시 DB로 확인). |
| 삭제 규칙 | `snapshot`의 전체 삭제뿐이다. |

### 2.2 `documents` — 저장한 PDF와 판독 결과

| 열 | SQLite 타입 | 제약 | 기본값 | 내용 |
|---|---|---|---|---|
| `id` | TEXT | PRIMARY KEY | 없음 | 문서 ID. `uuid4().hex` 32자(`saebom/store.py:260`) |
| `source` | TEXT | UNIQUE | 없음 | 원본 다운로드 URL. 같은 URL은 한 행만 가진다 |
| `name` | TEXT | 없음 | 없음 | 사이트가 준 첨부 이름(`download` 속성 값). 정리 전 원문 |
| `hash` | TEXT | 없음 | 없음 | PDF 본문 SHA-256 16진 64자 |
| `extraction` | TEXT | 없음 | 없음 | 판독 결과 JSON(4.2절) |
| `disk_path` | TEXT | 없음 | 없음 | 현재 PDF 절대 경로 문자열. 저장 위치 이동 시 갱신 |
| `kind` | TEXT | 없음 | 없음 | `"invoice"` 또는 `"contract"`. 옛 행은 `NULL` |

`DOC_COLUMNS = ("id","source","name","hash","extraction","disk_path","kind")`가 읽기·쓰기 모두의 열 순서다(`saebom/store.py:23`). `disk_path`, `kind`는 처음 `CREATE TABLE`에도 들어 있지만 옛 DB를 위해 `ALTER TABLE ADD COLUMN`도 둔다(6절).

| 구분 | 내용 |
|---|---|
| 쓰는 메서드 | `save_document`(`saebom/store.py:258`)가 `INSERT OR REPLACE`로 행 전체를 쓴다. 앱 코드의 호출처는 `Service.download_one`(`saebom/services/core.py:189`) 하나다. `_commit_root`(`saebom/store.py:370-373`)가 `disk_path`만 `UPDATE`한다. |
| 읽는 메서드 | `document(source=|id=)`(`:213`), `documents_by_sources`(`:225`, 900개씩 `IN` 조회), `_documents`(`:246`, `rowid` 순 전체), `path(doc)`(`:275`) |
| 교체 규칙 | 같은 `source`는 기존 `id`를 재사용해 행을 교체한다. `kind=None`으로 부르면 기존 행의 `kind`를 유지한다. `INSERT OR REPLACE`는 옛 행을 지우고 새로 넣으므로 `rowid`가 바뀌어 `_documents()`의 순서(마지막 등록 쪽)가 달라진다(임시 DB로 확인). |
| 삭제 규칙 | 행을 지우는 코드가 없다. PDF 파일은 저장 위치 이동 때 이전 사본만 지운다(8절). |

| 열 | SQLite 타입 | 제약 | 기본값 | 내용 |

## 3. `meta` 키 전체

`meta_get`/`meta_set` 호출 5곳과 `meta`에 직접 SQL을 쓰는 곳(`store.py`, `jobs.py`)을 `grep`으로 모두 찾았다. 이 PC의 실제 DB `meta`에도 아래 5개 키만 있었다(2026-10-26 조회).

| 키 | 값 형식 | 쓰는 곳 | 읽는 곳 | 비고 |
|---|---|---|---|---|
| `synced` | **평문** ISO 시각 문자열(JSON 아님) | `Store.snapshot` `saebom/store.py:85` | `Store.synced` `:108` | `meta_get("synced")`를 부르면 `JSONDecodeError`가 난다(임시 DB로 확인). 전용 메서드만 쓴다. |
| `document_root` | **평문** 절대 경로 문자열 | `Store._commit_root` `saebom/store.py:373` | `Store.document_root` `:291` | 키가 없으면 `<루트>/원본PDF`. `scripts/verify_ui.py:41`도 직접 `INSERT`한다. |
| `jobs` | JSON 사전(4.6절) | `JobRunner.persist` `saebom/jobs.py:60` | `JobRunner.__init__` `saebom/jobs.py:44` | `meta_get`을 쓰지 않고 `store.db.execute`로 직접 읽는다. |
| `local_invoice_folder` | JSON 문자열(따옴표 포함, 예 `"D:\\세금계산서"`) | `Service.set_local_folder` `saebom/services/local_audit_service.py:82` | `local_audit_state` `:52`, `run_local_audit` `:100`, `routes/local_audit.py:47` | 키 상수는 `LOCAL_FOLDER_KEY`(`saebom/services/common.py:31`). |
| `local_audit` | JSON 사전(4.5절) | `Service.run_local_audit` `saebom/services/local_audit_service.py:155` | `local_audit_state` `:61` | 키 상수는 `LOCAL_AUDIT_KEY`(`common.py:32`). 마지막 1건만 보관한다. |

`meta_get`/`meta_set`은 JSON 값 전용이다(`saebom/store.py:118-132`). 평문 키 두 개(`synced`, `document_root`)는 같은 `meta` 테이블에 있지만 읽고 쓰는 방식이 다르므로 새 키를 만들 때는 반드시 JSON 규칙(`meta_set`)을 따른다.

## 4. JSON 필드 내부 구조

아래 예시의 이름·금액·URL은 모두 가상 값이다. "확인" 열은 코드와 실제 DB에서 키 구성을 직접 본 곳이다.

### 4.1 `items.data`와 `contract_imports.data`

메일(`items.kind="mails"`). 만드는 곳은 `SiteClient.fetch_mails`(`saebom/site.py:155-162`)다.

| 키 | 타입 | 설명 |
|---|---|---|
| `id` | string | 행 `data-id` |
| `sender` | string | 첫 번째 셀 `innerText`(발신자) |
| `subject` | string | 두 번째 셀(제목) |
| `received` | string | 세 번째 셀(수신일, 예 `2026-10-01 09:12`) |
| `attachments` | array | `[{"name": 다운로드 이름, "url": 절대 URL}]`. 행의 `a[download]` 전부(PDF가 아닌 첨부도 포함) |

계약(`items.kind="contracts"`와 `contract_imports.data`). 만드는 곳은 `SiteClient.fetch_contracts`(`saebom/site.py:186`)다.

| 키 | 타입 | 설명 |
|---|---|---|
| `id` | string | 관리번호 |
| `kind` | string | 구분 셀. `"수입"` 또는 `"지출"` |
| `partner` | string | 거래처 |
| `title` | string | 계약명 |
| `period` | string | 셀 원문(예 `2026-01-01 ~ 2026-12-31`) |
| `amount_text` | string | 금액 셀 원문(예 `월 580,000원(부가가치세 별도)`) |
| `file` | object 또는 null | 첫 번째 `.pdf` 첨부 `{name, url}`. 없으면 `null` |

```json
{"id": "C-2026-901", "kind": "지출", "partner": "가나다정보(주)", "title": "보안관제 서비스 계약서",
 "period": "2026-01-01 ~ 2026-12-31", "amount_text": "월 1,000,000원(부가가치세 별도)",
 "file": {"name": "계약서_C-2026-901.pdf", "url": "https://sbgw.vercel.app/files/%EA%B3%84.pdf"}}
```

`catalog`가 응답에 붙이는 `pdfs`, `documents`, `candidates`, 계약의 `document`는 저장 값이 아니라 조회 때 계산하는 값이다(`saebom/services/compare_service.py:34-87`). `contract_imports()`가 붙이는 `imported`도 열 값을 합친 것이다(`saebom/store.py:190`).

### 4.2 `documents.extraction`

최상위는 `{fields, pages, error}` 세 키다(`saebom/compare.py:57,61,80,85`).

| 키 | 타입 | 설명 |
|---|---|---|
| `fields` | object | 필드 이름 → `{value, quote, page, method}`. 찾지 못한 필드는 키 자체가 없다. |

### 5.2 PDF 보관 폴더(`meta.document_root`) 아래

| 경로 | 내용 | 규칙 |
|---|---|---|
| `세금계산서/` | `documents.kind="invoice"` PDF | `files.KIND_FOLDERS`(`saebom/files.py:9`) |
| `계약서/` | `documents.kind="contract"` PDF | 같은 표. `kind`가 두 값이 아니면 `download_one`은 계약서 폴더를 쓴다(`saebom/services/core.py:180`) |
| `거래명세서/` | 앱이 만든 엑셀 | `files.STATEMENT_FOLDER`(`saebom/files.py:12`). `statement.build`가 `mkdir`(`saebom/statement.py:336`). DB에 등록하지 않고, 저장 위치를 바꿔도 옮기지 않는다 |

폴더 안 PDF 파일명은 **`{sha256 앞 12자}_{safe_name(name)}`** 이다(`saebom/services/core.py:182`, 이동 시 같은 규칙 `saebom/store.py:345`).

| 항목 | 규칙 |
|---|---|
| `safe_name` | `<>:"/\|?*`와 제어문자(0x00~0x1f)를 `_`로 바꾸고 160자로 자른 뒤 끝의 점·공백을 제거(`saebom/files.py:22-23`). 결과가 비어도 앞에 해시 접두어가 붙는다 |
| 같은 내용 | 해시가 같으면 파일명이 같아져 중복 저장하지 않고 `if not path.exists()`로 건너뜀(`saebom/services/core.py:183`) |
| 쓰기 | `{이름}.part`에 쓴 뒤 `replace`로 최종 이름으로 교체(`saebom/services/core.py:184-186`). 중간에 죽으면 `.part`가 남을 수 있다 |
| 이동 임시 파일 | `_prepare_root`가 `.saebom-write-{uuid}` 빈 파일로 쓰기 권한을 확인하고 `finally`에서 지움(`saebom/store.py:308-314`) |

거래명세서 파일명은 `거래명세서_{관리번호}_{거래처}[_{YYYYMM}-{YYYYMM}].xlsx`이며 계약기간 전체를 청구하면 월 범위를 생략한다. 같은 이름이 있으면 `_2`, `_3`을 붙이고 `"xb"` 모드로 새로 만들어 기존 파일을 덮어쓰지 않는다(`saebom/statement.py:267-272,339-356`). 템플릿은 `saebom/assets/거래명세서_템플릿.xlsx`이며(`saebom/statement.py:46-48`) 데이터가 아닌 배포 자원이다.

로컬 세금계산서 폴더는 사용자 PC의 임의 폴더이고 앱은 읽기만 한다(`saebom/local_audit.py:78-107`). 하위 폴더는 읽지 않고, `.pdf`·`.png` 최대 200개, 파일당 50MiB까지 읽는다.

### 5.3 경로 해석 우선순위

`Store.path(doc)`(`saebom/store.py:275-280`)는 ① 문서 ID로 `documents`를 다시 조회해 최신 행을 쓰고 ② `disk_path`가 있으면 그 경로, ③ 없으면 `<루트>/documents/{hash}.pdf`를 돌려준다. 존재 여부는 확인하지 않는다. 결과 JSON에 들어 있는 옛 `disk_path`는 이 최신 조회 때문에 저장 위치를 바꾼 뒤에도 유효하다. 반면 `Service._doc_path`(`saebom/services/core.py:158`)는 DB를 다시 읽지 않고 받은 문서 사전의 `disk_path`를 그대로 쓰므로 최신 행을 넘겨야 한다.

### 6.1 새 열을 추가하는 절차

1. `__init__`의 `CREATE TABLE` 문에 새 열을 추가한다(새 DB용).
2. 옛 DB용으로 `PRAGMA table_info(<테이블>)` 확인 후 `ALTER TABLE <테이블> ADD COLUMN <열> TEXT`를 실행하는 코드를 `saebom/store.py:67-70`처럼 추가한다. `NOT NULL`·기본값 없는 `TEXT`로 추가해야 `ADD COLUMN`이 실패하지 않는다.
3. **열 이름 없는 `INSERT`를 모두 고친다.** 위치 지정으로 쓰는 문장이 있다: `items`(`:84`, 3개 값), `meta`(`:85,132,373`, `jobs.py:60`, 2개 값), `contract_imports`(`:155`, 3개 값), `results`(`:429`, 3개 값). 열이 늘면 값 개수가 맞지 않아 `OperationalError`가 난다. `documents`와 `contract_status`는 열 이름을 명시한다.
4. `documents`에 열을 추가하면 `DOC_COLUMNS`(`:23`)에 넣고 `save_document`의 `INSERT OR REPLACE`가 새 값을 채우게 한다. `INSERT OR REPLACE`는 행 전체를 다시 쓰므로 빠뜨리면 다음 저장 때 새 열이 `NULL`로 돌아간다.
5. 읽는 쪽(`_row_to_doc` 등)과 4절의 JSON 구조를 이 문서와 함께 갱신하고, 새 열이 없는 옛 행(`NULL`)을 읽는 경로를 `tests/test_store_api.py` 형태의 시험으로 확인한다.
6. 옛 DB를 만든 앱 버전과의 왕복 호환은 보장하지 않는다(새 열이 있는 DB를 옛 코드가 열 때의 동작은 확인하지 않았다, 추정).

## 7. 트랜잭션·잠금 경계

| 대상 | 잠금 | 트랜잭션 | 비고 |
|---|---|---|---|
| 읽기 메서드 전부 | `with self.lock` | 없음(자동 커밋 상태에서 `SELECT`) | `saebom/store.py:94-465` |
| 쓰기 메서드 전부 | `with self.lock, self.db` | `with self.db`가 성공 시 커밋, 예외 시 롤백 | `snapshot`, `meta_set`, `save_*` |
| `set_document_root` | 이동 전 과정 `with self.lock` | DB 변경은 `_commit_root`의 `with self.db` 한 번 | 파일 복사는 트랜잭션 밖. 확정 전 실패하면 이번에 만든 복사본만 지움 `saebom/store.py:404-416` |
| `JobRunner.persist` | `store.lock` + `with store.db` | `jobs` 키 한 건 | `saebom/jobs.py:59` |
| `JobRunner.__init__`의 `jobs` 읽기 | `with store.lock` | 없음 | `saebom/jobs.py:43-44` |
| `JobRunner.exclusive` 블록 | 진입 검사 때만 `runner.lock`, 블록 동안은 쥐지 않음 | - | 새 작업 접수만 막는다 `saebom/jobs.py:128-139` |

잠금 획득 순서는 `JobRunner.lock` → `Store.lock` 한 방향뿐이다(`update`가 `runner.lock` 안에서 `persist`를 호출, `saebom/jobs.py:70-72`). 반대 방향(`Store.lock` 안에서 `runner.lock`)은 코드에 없어 교착 경로가 보이지 않는다.

# 07_auto "계약서 목록" 메뉴 구축 계획 (2026-10-21)

## Context
사용자는 그룹웨어 계약 문서함(`https://sbgw.vercel.app/#/contracts`)에서 계약서를 골라 가져와 앱 안에서 보는 **"계약서 목록" 메뉴**를 원한다. 가져올 때는 다음 조건으로 고를 수 있어야 한다.
- **최근 N개:** 관리번호가 큰 순
- **안 가져온 계약만:** 이 메뉴로 아직 가져오지 않은 관리번호
- **구분:** 전체/수입/지출

가져올 때는 목록만이 아니라 **계약서 PDF를 저장하고 판독**까지 한다.

**사이트 조사 결과 (2026-10-21)**
- 로그인 없이 열린다.
- 표 열: `관리번호/구분/거래처/계약명/계약기간/계약 금액/계약서`(7열), 행은 `tr[data-testid=contract-row][data-id]`
- 구분 필터: `#contract-filter`(전체/수입/지출)
- 현재 18건, 날짜 열은 없음

**기존 구조와의 관계**
- 기존 "목록 새로고침"(`Service.sync`)은 메일과 계약을 `items` 스냅샷으로 **전체 교체**한다. 그래서 가져온 계약 기록은 별도 테이블에 둬야 동기화 때 지워지지 않는다.
- PDF는 기존 `documents` 테이블을 그대로 쓴다(source URL 기준). 이 메뉴로 받은 계약서는 메일 비교 때 다시 다운로드하지 않고 재사용된다.

## 0단계 — 메인
- 이 계획을 `기획/계약서목록_구축계획.md`로 저장한다(07_auto 지침).
- 기준선을 확인한다: pytest 29건, 프런트 빌드.
- `07_auto` 세션이 같은 폴더를 동시에 고치지 않는지 사용자에게 한 번 더 알린다.

## 1단계 — 서브에이전트 2개 병렬 (파일 소유권 분리)

### 에이전트 B(백엔드) — 소유: `saebom/site.py`, `saebom/service.py`, `saebom/store.py`, `saebom/api.py`, 새 파일 `tests/test_contracts_import.py`
- **`site.py`:** `SiteClient.fetch_contracts(kind="전체")`에 구분 인자를 추가한다.
  - 기존 호출(`sync`)은 기본값으로 그대로 동작한다.
  - 페이지가 사이트 밖(about:blank 등)이면 `SITE_URL + "#/contracts"`로 직접 이동한 뒤 `#contract-filter`를 선택한다.
  - 열 7개 검사와 PDF 선택 규칙은 기존 것을 재사용한다.
- **`store.py`:** 새 테이블 `contract_imports(id TEXT PRIMARY KEY, data TEXT, imported TEXT)`를 둔다.
  - `imported_contract_ids() -> set`
  - `save_contract_import(item)`: `INSERT OR REPLACE`. data는 계약 행 JSON이고 imported는 `now()`.
  - `contract_imports() -> list`: 관리번호 큰 순.
  - 기존 `documents_by_sources`와 `path`를 재사용한다.
- **`service.py`:**
  - 모듈 함수 `contract_sort_key(id)`: `C-(\d+)-(\d+)`를 (연도, 번호) 숫자로 정렬하고, 맞지 않으면 문자열 뒤로 보낸다.
  - `select_contracts(items, limit, only_new, imported_ids)`: 순수 함수다. 처리 순서는 이렇다.
    1. only_new면 이미 가져온 ID를 제외한다.
    2. 관리번호 큰 순으로 정렬한다.
    3. limit이 있으면 앞에서 N개만 남긴다.
  - `import_contracts(job, kind, limit, only_new)` 작업
    - 처리: 사이트에서 목록을 수집하고 선택한다. 그다음 계약마다 `download_one(file, "contract")`로 PDF를 저장·판독하고 `save_contract_import`를 호출한다.
    - **PDF가 없거나 다운로드에 실패한 계약은 기록하지 않는다.** 그래야 다음 "안 가져온 것"에서 다시 시도된다. 실패는 `errors`에 모은다(기존 `download`와 같은 형식).
    - 진행률은 `update`로 갱신하고, 종료 요청이 오면 중단한다.
    - 선택된 것이 0건이면 "가져올 계약이 없습니다"로 정상 완료한다.
  - `contract_catalog()`: 가져온 계약 목록에 `document`(추출값, `available`)를 붙여 반환한다. 응답에서 `extraction.pages`는 비운다.
- **`api.py`**
  - `class ImportContracts(BaseModel)`: `kind: Literal["전체","수입","지출"]="전체"`, `limit: int|None = Field(None, ge=1, le=MAX_PAIRS)`, `only_new: bool=False`
  - `POST /api/contracts/import`: `service.submit("계약서 가져오기", service.import_contracts, kind, limit, only_new)`
  - `GET /api/contracts`: `service.contract_catalog()`
  - 두 경로 모두 기존 미들웨어(세션·비밀번호 잠금)의 보호를 받는다.
- **테스트:** `select_contracts` 조합(최근 N, 안 가져온 것, 둘 다, limit 없음, 정렬), store의 import 기록과 sync 뒤 유지, API 형식 검증(422), `contract_catalog`의 pages 비움.
  - 가짜 SiteClient와 기존 fixture PDF로 `import_contracts` 전체 흐름을 검사한다. 다운로드 실패 건이 기록되지 않는지도 확인한다.

### 에이전트 F(프런트) — 소유: `frontend/src/**`
- **`types.ts`:** `ImportedContract = {id, kind, partner, title, period, amount_text, file, imported, document: Doc|null}`
- **`App.tsx`:** NAV에 `{id:'contracts', label:'계약서 목록', icon: FileText}`를 추가한다. '비교 결과' 다음에 둔다. 페이지 제목과 설명 문구도 추가하고, `contracts` 화면을 렌더한다. 작업 접수는 기존 `act()`와 `busy`를 재사용한다.
- **`screens/ContractsScreen.tsx`(신규)**
  - 가져오기 조건 패널
    - 구분 select(전체/수입/지출)
    - 개수 입력(숫자, 비우면 전체, 1~500)
    - "아직 가져오지 않은 계약만" 체크박스
    - **계약서 가져오기** 버튼
  - 버튼 아래에 조건 요약 문구를 보여 준다. 예: "지출 계약 중 아직 가져오지 않은 최근 10개".
  - 가져온 계약 목록: 관리번호, 구분, 거래처, 계약명, 계약기간, 금액, 가져온 시각, PDF 상태(저장됨/파일 없음)를 보여 준다.
  - 검색(거래처·계약명)과 구분 탭을 둔다.
  - 계약을 선택하면 오른쪽에 상세를 보여 준다. 추출값(거래처, 사업자번호, 계약기간, 금액·부가세 조건, 지급 조건)과 기존 `components/Pdf.tsx`의 원문 뷰어가 들어간다.
  - 반응형은 기존 클래스(`panel`, `panel-heading`, `empty`, `field-label` 등)를 재사용하고, 꼭 필요한 스타일만 `style.css`에 추가한다.
- **데이터 갱신:** 화면이 열릴 때와, 작업 목록에서 '계약서 가져오기' 작업이 끝났을 때 `GET /api/contracts`를 다시 부른다. `useAppState`의 `state.jobs`를 사용한다.
- **완료 조건:** `npm run build` 통과. 기존 화면 문구·aria·className은 바꾸지 않는다.

### 공유 API 계약
```
POST /api/contracts/import  body {kind:"전체"|"수입"|"지출", limit:number|null, only_new:boolean} → {id: 작업ID}
GET  /api/contracts          → [{id, kind, partner, title, period, amount_text, file:{name,url}|null, imported, document:{id,name,extraction:{fields,pages:[],error},available,disk_path,kind}|null}]  관리번호 큰 순
작업 종류(kind) 문자열: "계약서 가져오기"
```

## 2단계 — 통합·검증 (메인)
1. `.venv/Scripts/python -m pytest -q`: 기존 29건과 새 테스트가 모두 통과해야 한다.
2. 프런트 빌드: `npm run build`.
3. **실제 사이트 검증:** 격리 데이터 폴더(`SAEBOM_DATA_DIR`, `SAEBOM_NO_OPEN=1`)로 서버를 띄운다. Playwright로 로그인한 뒤 '계약서 목록' 메뉴에서 다음을 확인한다.
   - 지출·최근 3개 → 3건(C-2026-040/039/038)이 생기고 PDF가 보인다.
   - "안 가져온 것만" + 최근 3개 → 다음 3건(037/036/035)이 온다.
   - 전체·안 가져온 것만·개수 비움 → 나머지가 모두 온다.
   - 다시 실행하면 "가져올 계약이 없습니다"가 나온다.
   - 원문 뷰어가 표시되고 JS 오류가 없다.
   - 이 검증은 `scripts/verify_contracts.py`로 남긴다.
4. 회귀 확인: `scripts/verify_ui.py`, `scripts/verify_raw_amounts.py`, 판정 불변 JSON 대조(scratchpad `baseline.py`).
5. 문서 갱신: `사용방법.md`(계약서 목록 사용법), `프로그램_기술설계서.md`(API·테이블·화면), 위키 `project-07-auto`.
6. EXE 재빌드: 실행 중인 `SaebomCompare.exe`를 사용자가 종료한 뒤 `scripts/build.py`로 한다.

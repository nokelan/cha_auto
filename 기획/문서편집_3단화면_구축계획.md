# 전송 전 문서 편집 3단 화면 구축 계획

작성일: 2026-10-26 / 상태: 구현·검증 완료(소스 기준, EXE 미반영) — 결과와 미검증 항목은 `MEMORY.md` 참고

## 1. 배경과 목표

- "계약서 목록"의 거래명세서·지출결의서는 확인 창에서 값을 보고 바로 생성·상신한다.
- 전송 전에 문서 내용을 **마크다운 편집기 + 워드형 편집 + 목차**의 3단 화면에서 고칠 수 있게 한다.
- 좌: 마크다운 편집기 / 중: 워드 문서 형태로 바로 수정 / 우: 목차(`#`, `##`, `###`만).
- 좌·중은 같은 문서를 양방향으로 동기화한다.

## 3. 사용자 결정(2026-10-26 질문 답변)

1. 지출결의서: 필드를 마크다운 문서로 구성해 보여 주고, 저장 때 다시 필드로 읽어 폼에 넣는다.
2. 거래명세서: 머리 정보 목록 + 품목 마크다운 표.
3. 워드형 편집기: TipTap + 마크다운 확장.
4. 전송 흐름: 기존 확인 창을 3단 편집 화면으로 대체한다(별도 "문서 편집" 버튼을 두지 않는다).

## 4. 설계

### 4.1 단일 원천은 마크다운 문자열

- 화면 상태는 `markdown: string` 하나다. 좌 편집기 입력과 중 편집기 변경이 모두 이 값을 갱신한다.
- 반대 방향 갱신은 `setContent(..., emitUpdate=false)`로 하고, 변경 출처 플래그로 되먹임 루프를 막는다.
- 초안(draft) → 마크다운 변환은 창이 열릴 때 한 번 한다. 이후는 사용자가 쓴 마크다운이 기준이다.
- 변환·역변환은 프런트의 순수 모듈 `docMarkdown.ts`가 맡는다. **서버 API와 검증(`statement.validate`, `expense.validate`, `build`)은 그대로 둔다.** 서버가 최종 검증을 하므로 편집기를 거쳐도 우회로가 생기지 않는다.

### 4.2 마크다운 서식(고정 템플릿, 필드명 한글 라벨)

거래명세서:

```
# 거래명세서
## 기본 정보
- 수신: (주)한울정보
- 작성 일자: 2026-09-30
- 청구 시작 월: 2026-01
- 청구 끝 월: 2026-12
## 품목
| 품목명 | 규격 | 월 금액 |
| --- | --- | --- |
| 유지보수 | 월 1회 | 190000 |
```

지출결의서:

```
# 지출결의서
## 기본 정보
- 제목: [IT기획팀] … 지출의 건 (26.09월)
- 청구·사용 월: 2026-09
## 금액
- 공급가액: 2100000
- 세액: 210000
- 합계: 2310000
## 첨부
- 계약서_….pdf
- 세금계산서_….pdf
## 특이사항
(자유 텍스트: 이 제목 아래의 나머지 전부를 원문 그대로 note로 사용)
```

- 역변환 규칙: 라벨(`수신:` 등)로 값을 읽고 순서는 따지지 않는다. 필수 라벨·표 머리글이 없거나 형식이 틀리면 **문제 목록**(기존 `problems[]` 방식)에 한글 문구로 표시하고 전송 버튼을 막는다.
- 읽기 전용 정보(계약기간, 사업자번호, 저장 폴더, 예상 합계·세액·줄 수, 중복 경고 등)는 문서에 넣지 않고 화면의 별도 안내 영역에 둔다. 합계는 현재 편집 내용에서 즉시 다시 계산해 보여 준다.
- 특이사항 안의 `#` 제목은 목차에도 나타난다(의도된 동작).

### 4.3 화면

- 신규 모달 클래스 `.doc-edit-modal`: `width:min(1500px,97vw); height:93vh`, 3열 `1fr 1.2fr 220px`, 각 열은 독립 스크롤.
- 좌(`region` aria-label "마크다운 편집"): 고정폭 글꼴 `<textarea>`. 별도 코드 편집기 라이브러리는 쓰지 않는다.
- 중(`region` "문서 편집"): TipTap(StarterKit 제목 1~3·목록·굵게, Table 계열 4종, 마크다운 직렬화). 워드 문서처럼 흰 종이 바탕·여백. `tabindex="0"`으로 Modal 포커스 순환에 포함한다.
- 우(`region` "목차"): 마크다운에서 `#`/`##`/`###`만 추출(코드 펜스 안은 제외)해 들여쓰기로 표시. 항목을 누르면 좌 편집기는 해당 줄로, 중 편집기는 해당 순번의 제목으로 스크롤한다. 정규식 대신 `marked`의 토큰 분석을 쓰면 `renderMarkdown.ts`의 헤딩 처리와 일치시킬 수 있다.
- 760px 이하: 열 대신 탭 3개(마크다운 / 문서 / 목차)로 전환한다. 하단 버튼 줄은 항상 보인다.
- Esc: 변경이 있으면 창 안 확인 줄("변경 내용을 버릴까요?")을 보여 준다(브라우저 `confirm` 대화상자는 쓰지 않는다).
- 모든 새 요소에 `data-testid`와 접근성 이름을 붙인다(`doc-editor-md`, `doc-editor-wysiwyg`, `doc-editor-toc`).

### 4.4 전송 흐름(기존 로직 재사용)

- `StatementModal`: 필드 입력부를 3단 편집 화면으로 교체. 생성 요청 본문은 역변환 결과를 기존 `StatementRequest`로 만들어 `POST contracts/{id}/statement`. 결과 화면(파일명·합계·내려받기·경고)과 `requesting` 닫기 차단은 그대로.
- `ExpenseModal`: 같은 방식. `phase`(input/running/result/failed/load-error), `submitLock`, 작업 진행 표시, 중복 경고, `site_draft` 안내는 그대로. 상신은 `POST contracts/{id}/expense`.
- 두 모달이 공유하는 3단 레이아웃은 `DocEditor` 컴포넌트로 분리해 props(`initialMarkdown`, `onChange`, 안내 영역 슬롯)만 받는다.

## 8. 위험과 미결정(가정)

- **마크다운 라운드트립 손실**: TipTap이 직렬화하며 공백·이스케이프를 바꿀 수 있다. 특이사항 텍스트가 `#f-note`에 들어갈 때 의도치 않은 `\` 이스케이프가 생기지 않는지 시험으로 확인한다.
- **`#f-note` 요소 종류와 사이트의 본문 조립 방식은 이 저장소에서 확인되지 않는다.** 실사이트 검증 단계에서 확인한다. 평문으로 렌더되므로 마크다운 서식은 사이트에서 서식 없이 원문으로 보일 수 있다(가정).
- 월 금액 표 셀에는 숫자만 허용하고 쉼표는 역변환에서 제거한다(기존 `parse` 규칙과 일치시킴).
- 거래명세서 12줄 제한과 검토 8항목은 서버·구조화 필드 기준이라 편집기에서 우회되지 않는다.
- 번들 용량 증가(TipTap/ProseMirror). EXE 재빌드 시 크기를 기록한다. 앱이 실행 중이면 종료 후 재빌드하며, 이번 계획 범위에는 EXE 재빌드를 넣지 않는다(요청 시 별도 진행).
- 범위 밖: 사이트 쪽 본문 템플릿 변경, 문서 서버 저장·이력, 이미지·mermaid 편집.

## 결론

**리팩토링은 필요하지만 급하지는 않다.** 백엔드(Python)는 계층이 잘 나뉘어 있고 동작도 안정적이다. venv에서 `pytest` 17건이 모두 통과했다. 반면 프런트엔드 `main.tsx`는 유지보수가 어려운 상태이고, 백엔드에는 데이터가 쌓일수록 느려질 지점이 몇 곳 있다.

범위: `saebom/` 4개 파일, `launcher.py`, `frontend/src/main.tsx`를 전부 읽었다. `tests/`, `scripts/`, `style.css`는 줄 수와 통과 여부만 확인했다.

## 1. 프런트엔드 `frontend/src/main.tsx` (가장 시급)

- **한 파일에 모든 것이 있다.** 403줄에 67KB이고, `App` 컴포넌트 하나가 `useState`를 약 25개 들고 있다. 목록·비교·이력·설정 화면과 모달 2개가 모두 이 컴포넌트 안에 있다.
- **JSX가 한 줄에 길게 이어진다.** 400자를 넘는 줄이 32개이고, 3단 화면(`:380`, `:385`)과 결과 화면(`:366`)은 한 줄이 수천 자다. diff 리뷰와 수정이 매우 어렵다.
- **주석 때문에 코드가 더 읽기 어렵다.** `/* [콜백 명세] App / onClick 이벤트 / 입력: () ... */`처럼 거의 같은 문구가 콜백 인라인에 수십 번 반복된다. 내용이 없는 정형 문구라서 명세 역할도 못 한다.
- **중복이 있다.** `toggle`(`:311`)과 `setAll`(`:329`)이 같은 Pair 생성 로직을 따로 가지고 있다. 판정 문자열 `'일치'` 등이 여러 곳에 흩어져 있다.
- **개선 방향:**
  - 파일을 `api.ts`, `types.ts`, `components/Pdf.tsx`, `AccessGate.tsx`, `screens/*`로 나눈다.
  - 상태는 `useJobs`, `useSelection` 같은 커스텀 훅으로 분리한다.
  - 의미 없는 인라인 콜백 주석은 정리하고, 핵심 함수의 명세만 남긴다.

## 2. 성능: 조회가 쌓일수록 느려지는 구조

- **`Service.catalog()`(`service.py:214`)**
  - `/api/state`가 작업 중에는 1초마다, 평소에는 8초마다 호출된다(`main.tsx:272`).
  - 호출할 때마다 계약 수만큼, 그리고 메일의 PDF 첨부 수만큼 `store.document()` 쿼리와 `Path.is_file()` 검사를 반복한다. 지출 계약마다 메일 수만큼 다시 순회하는 중첩 루프도 있다.
- **`/api/results`가 전체 이력을 반환한다.**
  - 매 폴링마다 모든 비교 결과를 JSON으로 파싱해 전송한다. 결과에는 페이지 전문 텍스트(`extraction.pages`)가 들어 있어 이력이 쌓일수록 무거워진다.
  - `Store.results()` 주석에도 "페이지네이션 없이 전체 반환"이라고 적혀 있다.
- **결과 한 건을 찾으려고 전체를 읽는다.** `correct`(`api.py:269`)와 `csv_result`(`api.py:316`)가 `store.results()` 전체를 읽고 `next(...)`로 찾는다. `Store.result(id)` 하나면 해결된다.
- **`run_compare`(`service.py:351`)의 그룹 계산은 O(n²)이다.** 행마다 전체 records를 돌며 `deepcopy`를 하는데, 이 안에 페이지 텍스트까지 들어 있다.
- **개선 방향:**
  - 문서 조회를 한 번에 묶어서 가져온다.
  - 이력은 목록용 요약과 상세 조회로 나눈다.
  - `Store.result(id)`를 추가한다.
  - 계약별로 그룹을 미리 만들어 둔다.

## 3. 하드코딩된 값

- **시작 비밀번호가 소스에 평문이다.** `api.py:145`의 `b"0000"`이다.
  - 4자리 숫자인데 시도 횟수 제한이 없다.
  - 로컬 전용 앱이라 위험은 낮지만, 설정값으로 빼고 변경 가능하게 하는 편이 좋다.
- **자사 사업자번호가 비교 로직에 박혀 있다.** `compare.py:107`의 `"000-81-00001"`이다. 양식이 바뀌거나 법인이 바뀌면 코드를 고쳐야 한다.
- **사이트 주소가 세 곳에 중복된다.** `SITE` 상수(`service.py:22`), `allowed_url`의 `"sbgw.vercel.app"`(`service.py:34`), `api.state`의 URL 문자열(`api.py:162`)이다. 한 곳에서만 정의하면 된다.
- **개선 방향:** `saebom/config.py`를 두고 비밀번호·사이트·자사 사업자번호·크기 제한(50MB, 100페이지, 500건)을 모은다.

## 4. 구조: `Service`의 책임 과다

`Service` 클래스가 (a) 작업 큐와 상태, (b) Playwright 브라우저 관리, (c) 사이트 DOM 수집, (d) PDF 다운로드, (e) 화면용 목록 구성, (f) 비교 오케스트레이션을 모두 맡고 있다.

- 사이트 수집 코드(`sync`)에서 메일과 계약의 DOM 읽기 JS가 거의 같은 모양으로 중복된다(`:186`, `:195`).
- 사이트 DOM이 바뀔 때 고칠 곳(`sync`)과 비교 규칙이 바뀔 때 고칠 곳(`run_compare`)이 한 클래스에 있어서 테스트하기도 어렵다.
- **개선 방향:** `SiteClient`(브라우저·수집), `DocumentService`(다운로드), `JobRunner`(작업 큐)로 나누고, `Service`는 조합만 하게 한다.

## 5. 함수 단위 정리

- **`compare.extract()`(`:49`)** 는 약 90줄이다. 세금계산서 분기와 계약서 분기를 `extract_invoice` / `extract_contract`로 나누는 것이 좋다.
- **`compare.compare()`(`:158`)** 는 `check()` 호출 뒤에 `checks[-1]["status"] = ...`로 결과를 덮어쓴다(`:224`). 암묵적 순서에 의존하므로 `check`가 판정을 직접 받도록 바꾸는 편이 안전하다.
- **`Store.set_document_root`(`:154`)** 는 약 70줄에 단계가 4개이다. 검증, 복사, 확정, 정리로 나눌 수 있다.
  - 문서 종류를 `doc["name"].startswith("세금계산서")`로 추측하는 부분(`:186`)이 취약하다. `documents`에 `kind` 열을 저장하면 해결된다.
- **파일명 정제 정규식이 중복된다.** `service.py:286`과 `store.py:189`에 같은 코드가 있다.
- **`launcher.main()`(`:31`)** 은 약 100줄에 중첩이 깊다. 중복 실행 처리, 서버 기동, 앱 창 감시를 함수로 나누는 것이 좋다. `__import__("hashlib")`(`:39`)는 일반 import로 바꾸면 된다.
- **잠금 범위와 UI 반응성:** `api.settings`(`:173`)가 `service.lock`을 잡은 채 PDF를 이동한다. 그동안 `/api/state`도 같은 잠금을 기다려 화면 갱신이 멈춘다.
- **오류 처리:** `close_browser`와 `browser()`에 `except Exception: pass`가 있고, `Service`에는 로깅이 전혀 없어 실패 원인이 `app.log`에 남지 않는다.
- **`pick_folder`(`api.py:188`)** 는 요청 처리 스레드에서 Tk를 만든다. 메인 스레드가 아니라서 환경에 따라 불안정할 수 있다.

## 6. 폴더·테스트 정리

- **`tmp/`가 112MB이다.** 안에 `source-comments/`(소스 사본)와 Chrome 확장 파일이 섞여 있다. `.gitignore` 대상이지만 정리하면 혼동이 줄어든다.
- **`새 폴더/`가 빈 폴더이다.** `documents/`는 프로젝트 루트에 있는 실사용 데이터로 보이니 용도를 확인한다.
- **테스트 환경:** 시스템 `python -m pytest`는 수집 오류로 실패하고 venv 경로로만 통과한다. `pytest.ini` 같은 설정을 두면 좋다.
- **프런트엔드 테스트가 없다.** 지금은 `scripts/verify_ui.py`뿐이라서, 1번을 하기 전에 화면 회귀 검사를 먼저 보강해야 안전하다.

# 07_auto — 계약서로 거래명세서 만들기 기능 계획

## Context

- 사용자는 계약서 PDF의 값으로 거래명세서 엑셀(`Ch14_거래명세서_템플릿.xlsx`)을 채우는 일을 반복한다. 04_hwpx 세션에서 만든 `contract-statement` 스킬(`~/.claude/skills/contract-statement/`, 스크립트 2개)의 규칙을 07_auto 앱(새봄 세금계산서·계약서 비교 앱)에 버튼 기능으로 옮긴다.
- 앱은 AI·OCR을 쓰지 않는다. 그래서 스킬에서 Claude가 하던 "원문 대조"는 **확인 창에서 사람이 고치는 단계**로 바꾼다.
- 사용자 결정(2026-10-21):
  1. 대상은 **수입 계약만**이다. 새봄바이오가 "을"(공급자)인 계약에서만 버튼을 켠다. 지출 계약에서는 버튼을 끄고 "거래처가 발행하는 문서"라고 안내한다.
  2. **확인 창에서 고친 뒤 생성**한다.
  3. 저장 위치는 **PDF 보관 폴더/거래명세서/**이고, 화면에 경로와 내려받기 링크를 보여 준다.
- 스킬에서 이미 정한 규칙(그대로 유지):
  - 작성 일자의 기본값은 계약체결일이다.
  - 행 일자는 청구월 말일이다.
  - 청구월은 `1월`로 쓰고, 해가 바뀌면 `26.03`으로 쓴다.
  - 한 장에 계약기간 전체(최대 12줄)를 넣는다.
  - F~H 수식과 공급자 칸은 손대지 않는다.
- 조사로 확인한 것(앱 fixture 계약서 15건):
  - 수입은 001·002·003이며 모두 월 금액, 부가세 별도다. 003은 2026-03~2027-02라 해가 바뀐다.
  - pdfplumber 원문에서 별첨1 `서비스명`/`대상`, `계약체결일 : [YYYY]년…`, 서명란 `사업자등록번호 갑 을`, `관리번호 :`를 안정적으로 읽을 수 있다. 견적서 표는 글자가 섞여 나와서 쓰지 않는다.
  - openpyxl은 .venv와 requirements에 없다.

## 설계

### 1. 백엔드 (Python)

**새 파일 `saebom/statement.py`**: 스킬의 `extract_contract.py`·`fill_statement.py`를 앱에 맞게 옮긴다.
- 읽기는 pdftotext 대신 저장된 `extraction.pages`(pdfplumber) 텍스트를 쓴다.
- 이미 추출된 값은 재사용한다: `extraction.fields`의 `start`/`end`/`amount`/`basis`/`vat_mode`(compare.extract_contract, `compare.py:125`).
- 정규식 토큰은 `compare.DATE`, `compare.BIZ`, `compare.integer`, `compare.norm`을 재사용한다.
- 함수:
  - `draft(doc, row)`: 계약 행과 문서로 확인 창 초기값을 만든다.
    - 반환값: `{contract_id, eligible, reason, customer, customer_biz, contract_date, issue_date(=contract_date), period_start, period_end, from_month, to_month, items:[{name, spec, monthly_amount}], notes:[], missing:[]}`
    - 수입 판정: 서명란 "을" 사업자번호가 `config.OWN_BIZ`이면 수입이고, 행의 `kind == '수입'`과도 맞춰 본다. 아니면 `eligible=false`이고 reason은 "지출 계약은 거래처가 발행합니다"다.
    - 품목: 제18조 "N. 이름: 월 금 X원"이 여러 줄이면 그대로 여러 품목으로 나누고 규격은 비워 `missing`에 넣는다. 한 줄이면 별첨1 서비스명·대상 + `amount`를 쓴다.
    - `basis=total`이면 notes에 "총액 계약 — 월금액 확인"을 넣는다. `vat_mode=included`이면 notes에 "부가세 포함 금액 — 공급가액 확인"을 넣는다.
  - `build(values, template, out_dir)`: 스킬 `fill_statement.py`의 채우기·검사 로직을 그대로 쓴다.
    - 저장하지 않는 경우: 청구월×품목이 12줄을 넘음, 자리표시자가 남음, F~H·25행 수식이 바뀜, 필수값이 빔, 월 금액이 정수가 아님. 이때 ValueError(한글 문구)를 낸다.
    - 문자열 칸은 수식 주입을 막는다(`=+-@`로 시작하면 앞에 `'`를 붙인다. api.py CSV `safe()`와 같은 규칙).
    - `fullCalcOnLoad=True`로 저장한다.
    - 파일명은 `거래명세서_{관리번호}_{거래처}.xlsx`(`files.safe_name`)다. 범위가 계약기간 전체가 아니면 `_{YYYYMM-YYYYMM}`을 붙인다. 같은 이름이 있으면 `_2`, `_3`을 붙여 덮어쓰지 않는다.
    - 반환값: `{file, path, rows, supply, vat, total, warnings}`
  - `template_path()`: `_MEIPASS` 또는 소스 기준 `saebom/assets/거래명세서_템플릿.xlsx`.
- **새 파일 `saebom/assets/거래명세서_템플릿.xlsx`**: `D:\ChaAI\04_hwpx\Ch14_거래명세서_템플릿.xlsx`(=스킬 `assets/template.xlsx`)의 사본.
- **`saebom/files.py`**: `STATEMENT_FOLDER = "거래명세서"` 상수를 추가한다.
- **`saebom/service.py`**: 계약 행과 문서를 찾아 statement에 넘기는 얇은 메서드 2개를 둔다.
  - `statement_draft(contract_id)`
  - `create_statement(contract_id, values)`
  - 행은 `store.contract_imports()`에서, 문서는 `store.document(source=row.file.url)`에서 찾는다. 생성은 `self.exclusive("거래명세서 생성")` 안에서 해서, 저장 위치 이동이나 다른 작업 중이면 400을 낸다.
- **`saebom/api.py`**:
  - 바디 모델 `StatementItem`, `StatementRequest{customer, issue_date, from_month, to_month, items}`
  - `GET /api/contracts/{id}/statement`: 초안. 없는 계약이면 404, 문서가 없으면 400.
  - `POST /api/contracts/{id}/statement`: 생성. 결과 JSON을 반환한다. 지출 계약이면 400.
  - `GET /api/statements/{file}`: xlsx를 내려준다(FileResponse, 한글 파일명). 파일명에 경로 구분자가 있거나 `.xlsx`가 아니거나 폴더 밖이면 404.

### 2. 프런트엔드 (React)

- **`types.ts`**: `StatementItem`, `StatementDraft`, `StatementResult`.
- **새 파일 `components/StatementModal.tsx`**: EditModal 구조와 클래스(`modal-backdrop`, `modal`, `edit-fields`, `modal-actions`)를 재사용한다.
  - 입력:
    - 수신, 작성 일자(date), 청구 시작·끝 월(month)
    - 품목 표: 품목·규격·월금액. 행 추가와 삭제 가능.
  - 실시간 표시:
    - 줄 수(청구월 × 품목, 12 초과면 빨간 경고와 생성 비활성화)
    - 예상 총계(공급가액·세액 10%·합계)
  - notes와 missing을 경고로 보여 준다.
  - 생성에 성공하면 결과를 보여 준다: 파일명, 저장 경로, 총계, 경고, `내려받기`(`<a href="/api/statements/{file}">`).
- **`screens/ContractsScreen.tsx`**: `ContractDetail` 제목줄에 `거래명세서 생성` 버튼을 넣는다.
  - 켜지는 조건: 수입 계약이고 원문이 있고 busy가 아님. 그 밖에는 꺼진 이유를 `title`과 작은 안내로 보여 준다.
  - 버튼을 누르면 초안을 GET해서 모달을 연다.
  - `busy`를 prop으로 받는다(App.tsx 405행에서 전달).
- **`style.css`**: 모달 품목 표·결과 영역 스타일. 1024px 이하에서는 1열.

- EXE 재빌드는 실행 중인 앱을 사람이 종료한 뒤 한다(지난번 원칙).

## 검증

1. **pytest 전체**(`.venv/Scripts/python -m pytest -q`): 기존 41건과 새 테스트가 모두 통과해야 한다. 새 테스트는 다음과 같다.
   - fixture 001·002·003 초안 값: 거래처, 계약체결일, 기간, 품목, 규격, 금액
   - 011(지출)은 `eligible=false`이고 POST가 400
   - 002로 만든 xlsx: 12줄, A~E 값, F~H·25행 수식 보존, 템플릿 원본 해시 불변
   - 003의 청구월 `26.03`~`27.02`
   - 13줄 이상이면 저장 안 함
   - 같은 이름 재생성 시 `_2`
   - 다운로드 API의 정상 동작과 경로 조작 거부
2. **프런트 빌드**: `npm.cmd run build`가 성공해야 한다.
3. **화면 검증**: 새 `scripts/verify_statement.py`가 격리 데이터 폴더에 fixture 002·011 문서와 가져오기 기록을 넣고 서버를 띄운다. Playwright로 다음을 확인한다.
   - 002에서 버튼 → 확인 창 기본값 → 생성 → 내려받기
   - 011은 버튼이 꺼져 있음
   - 390px 화면
   - 스크린샷을 `tmp/statement-review/`에 남기고 메인이 직접 열어 본다.
4. **결과 엑셀 육안 확인**: 개발 PC의 LibreOffice로 생성 xlsx를 PDF로 바꿔 열어 본다. 예상 총계는 002 기준 2,280,000 / 228,000 / 2,508,000이다.
5. 기존 `verify_ui.py`와 판정 회귀가 그대로인지 확인한다.
6. **미검증으로 남길 것**: 실제 그룹웨어 사이트에서 새로 가져온 계약, 엑셀 프로그램 화면, EXE 실행(재빌드 후 사람 확인).
